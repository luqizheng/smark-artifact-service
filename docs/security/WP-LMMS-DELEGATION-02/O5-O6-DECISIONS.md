## O-5：AS 侧 jti 消费绑定表（迁移 0006 + PgDelegationBindingStore）

### 裁决：**B（移除）——遵守 §5.1 冻结裁决"AS 不加表"，附带两项强制前置条件与一条再评估通道**

> 表述为完整方案：**本 PR 不合并迁移 0006 与绑定存储；契约修订新增"写路径 delegation 必带 caller_request_id（biz 配对强制）"红线；AS-4 接线以既有幂等机制（AS-1/AS-2）承接并发仲裁；若实施阶段以证据证明仍需 DB 兜底，按契约修订流程重新提案（可复用本表设计，其实现质量经 R2 验证合格）。**

### 裁决依据（逐项回答任务书六问）

1. **契约 v0.2 是否明确禁止 AS 加表？** 是。§5.1 明文"新表（ai-pm 自有 schema，独立迁移，**AS 不加表**）"。实现引用的"契约 §3.4"**不存在**（R2-F-04）——规范性前提失实，不能作为保留依据。
2. **该表承担什么职责？** "同 jti 异请求 → 硬拒 + 并发重放 DB 原子仲裁 + 复用取证"。R2 独立验证其实现质量**合格**（唯一约束仲裁 s14、窗口护栏 s20、purge 防护、失败关闭——分析见下），**质量不是问题；程序与架构位置才是**。
3. **移除后并发下是否仍能保证"最多一个 Fresh"？** 能——**条件是前置条件 1 落地**。既有机制已具备同等原子仲裁：AS-1 `artifact_key`/Idempotency 单事务端口、AS-2 `caller_request_id` 部分唯一索引（migration 0005，`create_generation_job_with_input` v2，既有并发回归通过）。并发防重放的仲裁点从"绑定表唯一约束"移到"业务幂等唯一约束"，强度等价（同为 DB 唯一约束原子判定）。
4. **能否以 AI-PM 为唯一权威状态存储？** 能（契约 §5.1 原设计：`pm_delegation` 签发记录 + 撤销记录在 AI-PM；AS 无状态 + 写路径在线撤销查询）。绑定表不是该模型的必要件，而是 AS 侧冗余兜底。
5. **若保留是否必须修订契约？** 是——必须新增 §3.4 完整章节（当前引用失实）、修订 §5.1 冻结文本、明确 consume 独立事务与业务事务的关系（端口文档声称"同一业务事务内先 consume 再写入"但端口 API **不暴露事务**，该表述当前不可实现——文档内部即不自洽）。
6. **表生命周期/约束/事务/清理是否安全？** 是：jti 唯一约束、配对 CHECK（s20 验证 23505/23514）、purge 1h 窗口护栏 >> token 最大有效窗（300s TTL + 60s 偏差 = ≤360s，1h 足够）、行消失时 fail-closed 重试、SECURITY DEFINER + search_path 固定 + 默认无 EXECUTE。**设计安全，但安全的设计不等于应当存在的表。**

### 为什么不是 A（保留 + 修订契约）

- 绑定表的真实安全增量 = "声明层 V10 被绕过/出错时的第二道闸 + 取证"。它的主要判定输入（caller_request_id/request_hash）恰恰来自尚未接线的声明层（O-6/V10）——**兜底先于主闸存在**，顺序倒置。
- 同指纹重放它**有意放行**（RetryAllowed，交业务幂等收敛）——它对"同 token 同请求并发重放"的唯一硬闸恰是业务幂等层本来就有的能力；异指纹复用的硬闸是 V10 声明层（接线后）本来就有的能力。两道主闸就位后，该表的边际防御收敛到"实现 bug 兜底"。
- 当前状态：零消费者（无任何路由调用 consume）——合并一个无消费者的迁移违反最小变更原则，且在 O-5 未裁决前制造"表已存在"的既成事实压力。
- 任务书明确："不得以实现已经完成为理由选择 A"——R2 独立分析也未找到必须保留的安全必要性（见第 3 点，等价仲裁能力已存在）。

### 强制前置条件（选择 B 的组成部分，非可选建议）

1. **PC-O5-1（契约修订）**：写路径 delegation 必须携带 `caller_request_id`（biz 配对强制，覆盖"无幂等键写端点 + 无绑定字段"组合——这是 R2 确认的 §3.1.2 分层真实缺口，绑定表正是冲着它来的；缺口必须堵，但堵在签发侧契约红线，不是 AS 加表）。AS-4 接线时写路径以 `caller_request_id` 驱动各端点幂等（create 路径将其映射为幂等键）。
2. **PC-O5-2（再评估通道）**：若 AS-4 联调/威胁评审证明需要 DB 兜底（例如幂等层无法覆盖的写端点出现），按契约修订流程重新提案——届时以本表设计为底稿，附 §3.4 完整章节、事务边界修订（端口暴露事务或明确两段式语义）与全部消费路由清单。

### 迁移处置

迁移 0006 尚未在任何共享环境执行（任务边界禁迁移动作；本地/CI 的 `sqlx::test` 每测试建独立库后丢弃，不构成"已执行"事实）。**未合并前移除无迁移回滚负担**（0001–0005 一字不动，sha256 清单不含 0006 的删除影响可忽略）。

## O-6：`biz.request_hash` 请求指纹扩展 claim

### 裁决：**修订后保留（CONDITIONAL KEEP）**——保留 AS 侧解析与校验实现，但须满足四项修订条件后方可进入 AS-4 接线

### 裁决依据（逐项回答任务书六问）

1. **request_hash 属于冻结契约吗？** **不属于。** §3.1.1 claims 冻结表无此字段；契约将其列为 O-6"待裁决；若采纳需并入 §3.1.1 并由 AI-PM 签发侧实现"。**当前任何依赖 request_hash 的安全声明都不具备契约授权**——实现与文档对此标注诚实（"超出契约，见 O-5"——注：该标注写的是 O-5，实为 O-6，笔误一处，随契约修订更正）。
2. **绑定哪些字段？** `method || path_with_prefix || caller_request_id || canonical_json(body)`（`delegation_request.rs:3-15`）。**不含**：URL query（现写端点均无 query——R2 逐一核对，无现实遗漏）、请求头（X-Project-Id 不入指纹——无安全影响：授权不依赖头，Q2；定位不一致由 require/Scoped 拦截）。
3. **规范化歧义？** 三处：① `path_with_prefix` 未定义**路径参数实例化形态**（模板 vs 实例化字符串）；② canonical JSON 依赖 serde_json 默认 BTreeMap（R2 核实 workspace 未启用 `preserve_order`——Rust 侧确定性成立 ✓），跨语言签发方需对齐浮点（ryu）与重复键（last-wins）语义，"含浮点/重复键拒签"目前**纯靠签发方自律，AS 不可检测**；③ 无算法/版本标识。
4. **字段遗漏/碰撞/重放？** SHA-256 无现实碰撞；重放=同指纹合法重试（交业务幂等，与 O-5 分析一致）；遗漏面=query（当前为零）+ 未来新增写端点的规范同步义务。
5. **签发时与执行时不一致风险？** 低——请求由 AI-PM 自己构造后签发（同源）；代理/HTTP 客户端层对 body 的任何重序列化差异会触发 AS 拒绝（fail-closed 方向正确，可用性问题非安全问题）。
6. **是否必须加版本号/算法标识/canonicalization 规则？** **必须。** 同仓 AS-2 caller fingerprint 已有版本字段先例（`create_generation_job_with_input` 的 fingerprint version 参数）——request_hash 无版本标识与仓内先例不一致，且未来 canonicalization 演进无法区分新旧指纹。

### 修订条件（全部满足才可接线；在此之前 request_hash 校验不得作为任何唯一防线——当前未接线，状态一致）

1. **PC-O6-1**：契约修订将 `biz.request_hash` + 顶层 `caller_request_id` 并入 §3.1.1（写路径条件必填 → 必填），明确"读路径不要求"。
2. **PC-O6-2**：指纹增加算法/版本标识（建议 `biz.request_hash_alg: "v1"` 或 `"v1:<hex>"` 前缀），冻结 path=实例化路径、query 不参与（带 query 的未来写端点必须同步修订规范）、body=serde_json Value 序列化（Rust 侧规范即本仓实现）。
3. **PC-O6-3**：AI-PM 签发侧实现同算法，双方交叉向量测试（同输入 → 同 64hex）。
4. **PC-O6-4**：AS-4 接线时 `assert_delegation_matches_request` 进入全部写路径（与 V10 同一接线任务，见 RELEASE-GATE G1）。

### 为什么不删除

request_hash 是"无幂等键写端点"威胁组合（O-5 分析第 3 点确认的真实缺口）在**签发侧**的正确补 half：caller_request_id 绑定"哪次操作"，request_hash 绑定"该操作的精确内容"，两者配合使"截获 token 后改 body 重放"在声明层即被拒绝，且不要求 AS 持久化任何状态——与候选 B"AS 只验证凭证并执行"的职责边界自洽。删除将把防重放完全推回 TTL+撤销+各端点幂等，对 artifact:create（Idempotency-Key 可选）组合重新开洞。

## 两项裁决的联合形态（R2 推荐目标态）

```
AI-PM（唯一签发方，唯一授权状态存储）
  └─ 写 delegation 一律：caller_request_id + request_hash(v1) + 绑定字段 + jti（pm_delegation 落库 fail-closed）
AS（无新增持久化授权状态）
  └─ 写路径：V1–V9 → V10 声明层一致性（caller/hash/artifact/operation 四比对）→ V11 在线撤销 → 业务幂等（caller_request_id 驱动，DB 唯一约束并发仲裁）→ 写入 + 审计(含 jti)
```

契约修订清单（汇总，见 CONTRACT-CONSISTENCY §5）：O-5 删表、O-6 按 PC-O6 并入、`actor_type` 入表或移除、修正 §9 证据表、修正 O-5/O-6 交叉笔误、V5 补 leeway 语义、读端点豁免清单。
