## 0. 复审结论

**总裁决：Changes Required。v2 不能作为实施基线。**

v2 已正确修复 v1 最重要的 deadline_exceeded 二次提交错误，也正确坚持 PostgreSQL 唯一状态权威、Worker 最小权限、Executor 与外部副作用分离等方向。但仍存在四项实施阻断：

1. **DB 契约缺陷：deadline 与 cancel 竞争会留下不可领取的 retry_wait Job。** heartbeat 的 deadline 分支经 settle_failed_attempt 推进 retry_wait，但不清除 cancel_requested_at；claim 明确要求 cancel_requested_at IS NULL。该 Job 不会重领，只可能等 expires_at 到期后被 QUEUE_EXPIRED 收尾。
2. **INV-1 安全锚点错误。** 以 heartbeat 响应接收时刻加 L 推算租约到期，会把 RPC 往返耗时误算为额外租约。终止安全边际 M=12s 只覆盖进程终止预算，未覆盖最多 T=10s 的请求耗时。
3. **INV-2 低估连续失败耗时。** 配合文档指定的固定延迟/Delay 调度，两次连续 RPC timeout 的最坏耗时不是 2H+T，而是至少 K(H+T)。当前参数 2×(15+10)=50s，大于 L−M=48s。
4. **短 deadline 无可靠本地单调钟换算。** claim 返回 deadline_at 和 lease_expires_at 两个数据库绝对时间戳，但没有返回 DB now/started_at/remaining duration。v2 用 deadline_at−started_at 计算剩余执行时间，而 claim 返回列中没有 started_at。max_execution_seconds=1 时 lease 会被夹到 deadline，Supervisor 无法仅凭当前响应证明它会在 lease 失效前停止 Executor。

在这些阻断关闭前，不得把 ART-03B-02 描述为可实施基线，更不得启动生产生成执行路径。

## 1. 0003 SQL 事实（本次直接核验）

### 1.1 heartbeat_generation_job

函数顺序为：

1. 校验 lease_seconds 与 token；
2. 锁定 Attempt，检查存在、status=running、token hash；
3. 锁定 Job，检查 status=running；
4. **先检查 deadline**：若 now >= deadline_at，调用 settle_failed_attempt(..., 'timed_out', 'GENERATION_TIMEOUT', ..., true, ...) 后返回 deadline_exceeded；
5. 再检查 lease_expires_at 是否为空/已过期，过期则 stale；
6. 更新 Attempt 与 Job heartbeat/lease；
7. 最后检查 cancel_requested_at，存在则返回 cancel_requested，否则 renewed。

结论：
- deadline_exceeded 返回前数据库已收尾 Attempt；Worker 必须 KillOnly，禁止再次 complete/fail/confirm。
- 正确 token 且 deadline 已到时，即使 lease 已过期，也会先走 deadline 收尾；错误 token 不会触发收尾。
- cancel_requested 返回前已续租。
- heartbeat 的 renewed/cancel_requested 只可能在本次 heartbeat 事务观察到 Attempt/Job 仍 running 且 lease 有效后返回。

### 1.2 complete / fail / confirm

- complete：Attempt/token → Job running 且 lease 未过期 → cancel_requested → 输出登记验证 → succeeded。lease 过期返回 stale；cancel_requested 不终态化。
- fail：Attempt/token → Job running 且 lease 未过期 → cancel_requested → 错误码格式 → retryability 白名单 → settle。lease 过期返回 stale_attempt；Job 不存在返回 not_found。
- confirm_generation_job_cancelled：检查 Attempt running + token、Job running、cancel_requested_at；**不检查 lease 是否过期**。返回 cancelled / not_requested / stale。
- confirm 的 not_requested 不是 SQL 不可能状态：当前 Worker 正常序列下它不应发生，但 SQL 函数明确允许它；任何有权更新 Job 的其他写入路径都可能清除/改变请求标记。Worker 必须定义保守处理，不得把 not_requested 当作 cancelled。
- request_generation_job_cancel：running 时用 coalesce 写 cancel_requested_at；本迁移函数组没有清除该字段的语句。该标记在当前契约下是持久的。

### 1.3 重试白名单与角色权限

- is_retryable_generation_error 白名单只有 GENERATION_TIMEOUT、STORAGE_UNAVAILABLE。
- fail_generation_job_attempt 的 p_retryable=true 只是必要条件之一，仍须错误码命中白名单且 attempt_count < max_attempts、expires_at 允许；不能绕过白名单。
- Worker role 仅获七个受控函数 EXECUTE；db-roles.sql 显式 REVOKE ALL PRIVILEGES ON ALL TABLES、默认权限 REVOKE ALL、REVOKE CREATE。没有业务表 DML 授权。
- 本次分支与 main 的 migrations.sha256 文件内容完全一致；0003 SQL blob SHA 相同。迁移文件未被修改。

## 2. 必须修订的数据库契约问题：deadline × cancel

### 2.1 可复现逻辑

给定 Job 正在 running，cancel_requested_at 非 NULL，heartbeat 在 deadline 到达后执行：

- heartbeat 的 deadline 判断先于 cancel 判断；
- deadline 分支调用 settle_failed_attempt(... GENERATION_TIMEOUT, retryable=true)；
- settle_failed_attempt 可能把 Job 状态改为 retry_wait，但不清除 cancel_requested_at；
- claim_generation_job 的候选复核条件包含 cancel_requested_at IS NULL；
- 因此 retry_wait Job 被永久排除在 claim 之外，直至 expires_at 到期；
- recover_expired_generation_jobs 的队列过期分支最终会将其置为 cancelled / QUEUE_EXPIRED，但这不是文档所称的正常超时重试。

### 2.2 约束与处置

这是 Migration 0003 的既有契约缺陷，不是 Worker 能修复的状态机问题。本阶段禁止改写 0003，因此：

- Worker 收到 deadline_exceeded 仍必须 KillOnly + 零 DB 写；不得尝试清除 cancel_requested_at 或补交 fail。
- 文档不得再声称此竞争下 Job 会正常 retry_wait 后被重新 claim。
- 登记为 **DB-BLOCKER-01**：需单独提出新 Migration（例如 0004）修复策略并经独立评审。候选语义必须由产品/业务确认：取消请求优先（deadline 分支将 Job cancelled），或 deadline 优先（清理取消标记并允许超时重试）。不得在本设计里自行选择。
- 在 DB-BLOCKER-01 关闭前，凡依赖 deadline/cancel 竞争后自动重试的验收均不得通过。

## 3. 终态提交不确定性协议修订

### 3.1 可保留的正确性结论

在 0003 当前 SQL 下，若 complete/fail 的终态事务已成功提交，Attempt 已不再是 running，Job 也不再是 running（complete 为 succeeded；fail 为 retry_wait/failed/timed_out）。随后 heartbeat 会返回 stale，而不会返回 renewed。

因此，对**确实属于传输层结果不确定**的提交调用：
- heartbeat=stale：放弃，不再写 DB；但不声称知道原提交是否落地。
- heartbeat=renewed：原 complete/fail 没有成功完成终态转换，可进入受限补交判定。
- heartbeat=cancel_requested：进入取消收尾。
- heartbeat=deadline_exceeded：DB 已收尾，KillOnly + 零 DB 写。
- heartbeat 自身错误/超时：KillOnly + Abandon，等待 DB 恢复扫描；不得继续无限探测。

### 3.2 必须补上的错误分类

v2 把“Err”过度笼统地归入 Uncertain。实现必须区分：
- **传输不确定**：请求可能未到达、事务可能提交但响应丢失。允许走 heartbeat 探针。
- **明确数据库拒绝/确定性业务错误**：例如 INVALID_OUTPUT_SHA256、OUTPUT_NOT_REGISTERED、INVALID_ERROR_CODE 等明确 PostgreSQL 错误响应。不得把它们当成网络不确定后自动重放；应记录确定失败原因并按明确错误路径处理。
- **本地协议/序列化错误**：请求未能发送时可确认未提交；修正/终止路径由错误类型决定，不得盲目重复。

### 3.3 补交安全边界

heartbeat=renewed 只证明探针事务观察时 Attempt/Job 仍 running 且租约有效；它不保证未来补交时租约仍有效。补交必须：
1. 只允许一次；
2. 只允许对原始请求字节/参数完全相同的提交进行；
3. 结果文件及 SHA-256 快照必须冻结，补交期间禁止 Executor 再写；
4. 补交调用必须有独立 RPC timeout；
5. 若补交返回 stale/stale_attempt/not_found 或再次传输不确定，停止提交并放弃；不得第三次提交；
6. 若补交返回 cancel_requested，转 KillOnly + 死亡确认 + confirm；
7. 不把租约恰好过期解释为可重试提交；数据库返回 stale 即失去提交权。

注意：租约在探针后、补交前过期时，补交会被 DB 拒绝。这是允许的安全结果，但可能丢失本地结果并由恢复扫描重跑；不能承诺“renewed 就一定能成功补交”。

### 3.4 U4 stale 二义

stale 可能表示原终态提交已落地，也可能表示 lease/Attempt 已失效。两种情况的共同安全动作是：
- 停止所有后续 DB 写；
- 终止 Executor（若仍活着）并执行死亡确认；
- 不删除仍可能被进程写入的目录；
- 等待 DB 权威状态/恢复流程收敛。

两者动作同构仅在“零 DB 写、终止执行”层面成立；**清理、审计、是否已成功交付**并不同构。不得声称 stale 已证明业务成功或失败。若需要知道终态，需未来受控只读状态函数（DR-7），不是直接 SELECT。

## 4. Supervisor FSM 必须补齐的状态与边

以下作为规范状态，不允许只在自然语言中描述：

| 状态 | 输入/结果 | 必须动作 | 下一状态 |
|---|---|---|---|
| Claiming | 无 Job | 无 Attempt，回 Idle/维护循环 | Idle |
| Claiming | claim RPC 传输不确定 | 不假定 claim 未创建 Attempt；不得凭本地猜测重领同一 Job；停止本轮 claim，等待租约恢复/维护扫描 | ClaimUncertain |
| Claiming | claim 明确 DB 错误 | 失败告警/退避，不创建 Executor | Idle/Degraded |
| Claimed | 创建目录失败 | 若仍持有权且 lease 安全窗口充分，按确定失败策略；否则零写放弃 | SubmitFail 或 Abandon |
| Spawning | spawn 失败且确认未创建进程 | fail 仅使用稳定错误码且遵守 DB 白名单 | SubmitFail |
| Spawning | spawn 返回不确定/子进程句柄丢失 | 按进程发现与平台原语定位；无法证明无进程则 KillOnly + hard gate | Kill/Abandon |
| Executing | heartbeat renewed | 更新安全计时锚点（请求发出时刻，见 §5） | Executing |
| Executing | heartbeat cancel_requested | KillOnly；死亡确认后 confirm | CancelSequence |
| Executing | heartbeat deadline_exceeded | KillOnly + 零 DB 写 | Abandon |
| Executing | heartbeat stale | KillOnly + 零 DB 写 | Abandon |
| Executing | Executor 成功/失败/协议错误 | 冻结输出快照、确认进程树退出，再按对应提交路径 | SubmitComplete/SubmitFail |
| Submit* | 明确 DB 返回 | 按完整返回枚举处理；不能把 cancel_requested 当终态 | Settled/CancelSequence/Abandon |
| Submit* | 传输不确定 | 进入 Uncertain，仅探针一次 | Uncertain |
| Uncertain | probe renewed | 冻结快照不变时最多补交一次 | SubmitRetryOnce |
| Uncertain | probe cancel_requested | KillOnly + 死亡确认 + confirm | CancelSequence |
| Uncertain | probe deadline_exceeded | KillOnly + 零 DB 写 | Abandon |
| Uncertain | probe stale | KillOnly + 零 DB 写；终态成因未知 | Abandon |
| Uncertain | probe 明确错误/超时 | KillOnly + 零 DB 写 | Abandon |
| CancelSequence | 死亡确认失败 | 不 confirm、不清理；停止 heartbeat；等待 lease/recovery；继续告警 | AbandonPendingRecovery |
| CancelSequence | confirm cancelled | Settled | Settled |
| CancelSequence | confirm stale | 不再写；等待恢复扫描 | Abandon |
| CancelSequence | confirm not_requested | 不得声称 cancelled；不再 confirm 循环；停止 heartbeat，零写放弃并告警，等待 lease recovery | Abandon |
| Any live state | shutdown drain expires | KillOnly + 死亡确认；确认成功后零写放弃，确认失败则目录保留 | Abandon |
| Any state | Supervisor crash | 平台进程树/容器机制回收；DB 恢复扫描负责状态收敛 | ExternalRecovery |

特别约束：
- 每 Attempt 的 complete/fail/confirm 总调用次数必须有形式化上界；补交只允许一次，confirm 也只允许在 cancel_requested 控制流中一次补偿式确认。
- confirm 的 not_requested 是可达返回值，不能按“不可达”处理。建议保守动作是零写放弃，等待租约恢复；不能调用 fail(EXECUTOR_KILLED)。
- claim 本身的传输不确定也必须有状态，不能遗漏“DB 已 claim 成功但 Worker 没收到 token”的窗口。

## 5. Lease / Heartbeat 时序不变式重写

### 5.1 INV-1 安全锚点

v2 使用 heartbeat **响应接收时刻**作为 last_renew_local 锚点不成立：响应可能在 DB 更新租约后经过接近 T 的网络/排队延迟才到达；从响应接收时刻再加 L 会把这段耗时错误地加回租约。

对于未被 deadline 夹逼的完整 lease，保守锚点应是**请求发出时刻**：
- 记录 heartbeat request send 的 monotonic instant；
- DB 续租发生在请求发出之后，因此 DB lease expiry 不早于 send_time + L（仅适用于 lease 未被 deadline 截短）；
- 终止必须在 send_time + L − M 前发起，M 覆盖完整终止/死亡确认预算。

不能把 RPC response receive 当作租约起点。不能把 M 同时重复或不完整地用于吸收 RPC 延迟。

### 5.2 INV-2 连续失败预算

在固定延迟调度（一次 RPC 完成/超时后再等待 H 才发下一次）下，K 次连续失败最坏预算至少为：

**K × (H + T) ≤ L − M**

而不是 K×H+T。若采用绝对固定频率调度，必须给出调度器语义、错过 tick 的行为、RPC 不重叠证明和独立推导，不得套用 Delay 的公式。

当前值：
- L=60, H=15, T=10, K=2, M=12
- K×(H+T)=2×25=50
- L−M=48
- **不成立，差 2 秒，且没有调度抖动余量。**

建议后续重新选参；候选例如 L=80、H=20、T=10、K=2、M=12，得到 60≤68，但仍须将调度抖动、进程终止实测上界、OS 暂停/CPU 饥饿预算加入 M 或单列安全余量后验证。此候选不是已批准参数。

### 5.3 短 deadline 的阻断

claim_generation_job 返回 lease_expires_at、deadline_at，但没有返回 DB now、started_at 或剩余 deadline duration；也没有返回 max_execution_seconds。v2 的计算 deadline_at−started_at 在 claim 返回契约中不可执行。

当 max_execution_seconds=1 且 lease_seconds=60：
- DB 将 lease_expires_at 截短到 deadline_at；
- Worker 不能仅用本地 monotonic clock 得到这一秒的剩余时长；
- heartbeat 周期若为 15 秒，不能保证 Executor 在 1 秒 lease/deadline 前停止；
- 用本机 wall clock 比较 DB 绝对时间戳，必须先定义并强制 DB/host 最大时钟偏差及 RPC 时延预算，v2 没有该约束。

因此 **DB-BLOCKER-02**：在不修改 0003 的前提下，v2 无法证明短 deadline 的“先停后失约”。后续可通过新受控函数返回 DB server_now/remaining duration，或设计经验证的时钟偏差协议解决。当前不得声称 INV-1 覆盖 max_execution_seconds=1。

## 6. 进程树回收修订

### 6.1 Linux

- process group kill 只能覆盖仍留在该 PGID 的进程；setsid/setpgid、双重 fork、脱离组的后代可逃逸。
- PDEATHSIG 只保护设置它的直接进程；链式保护要求每一代子进程都正确设置并检查父 PID，不能假定 Node/第三方库的孙进程都遵守。
- **PID 1 只负责收养/回收孤儿僵尸，不会自动杀死仍在运行的孤儿进程。** 不得把“PID 1 收尸”列为进程终止层。
- cgroup v2 的 cgroup.kill/容器销毁才是生产全树兜底；必须防止 Executor 获得迁移 cgroup、写 cgroup.procs 或访问宿主控制面能力。
- 非容器开发环境下，若存在 setsid 逃逸者且无 cgroup 管控，不得声称进程树死亡确认成功；应 fail closed，不清理目录、不 confirm。

### 6.2 Windows

挂起创建 → AssignProcessToJobObject → Resume 可避免 Executor 在未加入 Job 时执行，但实现还必须：
- Job 句柄不可被子进程继承或复制；确认关闭 Supervisor 的最后一个 Job handle 才触发 KILL_ON_JOB_CLOSE；
- 不设置 BREAKAWAY_OK / SILENT_BREAKAWAY，验证子进程不能脱离 Job；
- 明确 Worker 自身处于外层 Job 时的嵌套 Job 兼容策略；不支持时启动 fail-fast；
- 测试孙进程、双重 spawn、关闭最后一个句柄、Supervisor crash、外层 Job 场景。
KILL_ON_JOB_CLOSE 在成员关系未被 breakaway 的前提下覆盖 Job 内后代；不能脱离上述前提作无条件表述。

### 6.3 死亡确认失败与回收

hard gate 本身正确，但不能承诺取消“必然很快完成”：
- confirm 不调用；heartbeat 停止；等待租约过期；
- recovery worker 必须持续运行，且 DB 可达，才会在恢复扫描中按 cancel_requested_at 将 Job 置 cancelled；
- 如果 DB/恢复扫描长期不可用，取消终态会延迟；
- 目录不得因 7 天 TTL 自动删除仍可能存活进程使用的路径。开发持久目录不能仅凭 mtime 删除；无 DB 只读证明能力时只能保留并告警，或使用每 Worker 可整体销毁的临时容器/volume。
- D 状态进程可能长时间不响应 SIGKILL；cgroup kill 也不能承诺立即消除不可中断内核等待。必须将此作为平台残余风险，而非有限时间保证。

## 7. 纯计算与副作用边界

Executor 纯计算是必要条件，但“无凭据”不等于“无网络能力”，也不等于“无法写共享文件系统”。

正确表述：
- 03B-02 定义进程、环境、FD、Attempt 私有目录和 IPC 边界；
- 03B-03 必须真正实施网络拒绝、只读根、挂载白名单、cgroup/容器销毁、资源限额；Executor 不可访问宿主 socket、Docker socket、云 metadata、共享写卷或服务凭据；
- 03C 只能在受限目录中做本地计算，禁止运行时安装依赖；
- 03D 是唯一业务副作用路径，负责上传/finalize/安全检查/READY/幂等补偿；
- “两个 Attempt 不会同时产生外部副作用”只能在 03B-03 隔离已经实测生效、03C 无绕过能力、03D 所有副作用受 DB 幂等与授权约束后成立。03B-02 单独完成不能证明该命题。

## 8. 阶段边界与生产门禁

| 阶段 | 必须负责 | 不得推给下一阶段的责任 |
|---|---|---|

## 10. 原文中“声称已解决但实际未解决”

1. **“deadline/cancel 竞争两路径互斥且都闭合”**：SQL 的 deadline 分支不会清除 cancel_requested_at；Job 进入 retry_wait 后 claim 永远排除它，直到 queue expiry。
2. **“heartbeat renewed 证明原终态提交必未落地”**：只对成功终态提交与限定的传输不确定成立；不能覆盖所有 Err，必须分类。
3. **“补交一次安全”**：探针与补交之间 lease 可过期；DB 会拒绝补交，结果可能丢失，不能声称一定挽救。
4. **“PID 1 收尸是进程树回收层”**：PID 1 回收僵尸，不会杀活进程。
5. **“Linux 四层确保整树回收”**：pgid 与链式 PDEATHSIG 可被脱组/未配合孙进程逃逸；只有 cgroup/容器边界能提供生产兜底。
6. **“Windows KILL_ON_JOB_CLOSE 无条件递归”**：必须禁 breakaway 并确保最后一个 Job handle 关闭，且处理嵌套 Job。
7. **“死亡确认失败不会造成取消悬挂/目录泄漏”**：只能依赖 DB recovery 持续运行；7 天 mtime 清理不能证明进程已死。
8. **“INV-1 不依赖 DB 可达性且已证明先停后失约”**：本地锚点与 deadline clamp 论证均不成立。
9. **“INV-2 余量 8 秒”**：Delay 调度的两次 RPC timeout 至少需要 50 秒，当前仅有 48 秒。
10. **“max_execution_seconds=1 已由 min() 处理”**：claim 未返回可供单调钟换算的剩余 deadline duration。
11. **“两个 Attempt 不可能同时产生外部副作用”**：只靠纯计算声明与凭据剥离不能证明网络/文件系统隔离。
12. **“测试策略逐行覆盖矩阵”**：缺少上述新增边界与竞争用例；P-03 只测 DB 已收尾，不覆盖 cancel 标记残留造成的不可领取。

## 11. 必须关闭的 BLOCKERS

- **DB-BLOCKER-01**：deadline 与 cancel 竞争导致 retry_wait + cancel_requested_at 非 NULL，claim 不可领取。由独立 DB 设计提出 0004 修复；本 PR 不修改 Migration。
- **DB-BLOCKER-02**：claim 未提供可靠的 DB 时间锚点/剩余 deadline duration，无法证明短 deadline 下先停后失约。提出受控契约修复或正式的有界时钟偏差协议。
- **TIMING-BLOCKER-03**：修正 heartbeat request-send 锚点与连续 RPC timeout 预算；重新计算参数并给出调度器可执行语义及最坏时序证明。
- **PROCESS-BLOCKER-04**：Linux 生产全树回收依赖 03B-03 cgroup/容器能力；未实测前不得将 03B-02 单独验收为进程树安全完成。
- **FSM-BLOCKER-05**：补齐 claim 不确定、spawn 不确定、confirm not_requested、补交租约过期、死亡确认失败和清理失败路径的状态/计数上界。

以上 BLOCKER 关闭前，裁决保持 Changes Required。当前文档只可作为讨论稿，不可作为实施基线。
