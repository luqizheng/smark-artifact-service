# ART-04A — Durable Generation Request Correlation and Exact Version Result Contract

> **Status:** Proposed API contract / Draft; architecture clarification only; not implementation approval.
> **Date:** 2026-11-25
> **Parent:** ART-04 AI-PM GenerationJob Control Contract
> **Scope:** Closes the API-design portions of AR04-01 and AR04-02. Does not close their implementation gates.

## 1. Decision summary

ART-04A proposes two additive GenerationJob contract changes:

1. Add a durable `caller_request_id` to GenerationJob creation and a lookup endpoint. This is the permanent business correlation identity; `Idempotency-Key` remains a short-lived HTTP retry mechanism.
2. Expose the existing internal `target_version_id` in the public GenerationJob response. The field is nullable while no target Version has been allocated, but once assigned it is immutable. A Job may not transition to `succeeded` unless the exact target Version is known and its output commit has succeeded.

These changes preserve the service boundary: AI-PM owns the request identity and business intent; Artifact Service owns the Job and Version lifecycle.

## 2. AR04-01 — Durable request correlation

### 2.1 Two identities, two different purposes

| Field | Purpose | Lifetime |
|---|---|---|
| `Idempotency-Key` header | Deduplicate short-window HTTP retries and replay the original response | Existing documented retention: at least 24 hours |
| `caller_request_id` body field | Identify one durable caller business operation and recover an uncertain create after process/service outages | Retained for at least the lifetime of the Job and its audit/correlation record |

The two values MUST NOT be treated as interchangeable. An idempotency cache is not the durable business-operation ledger.

### 2.2 Caller contract

Add required `caller_request_id` to `CreateGenerationJobRequest`:

- UUID generated and persisted by AI-PM before the first outbound request.
- One ID represents exactly one intended GenerationJob creation, not a whole Task, Run, or multi-step orchestration.
- AI-PM MUST reuse the same ID for every retry/reconciliation of that intended Job.
- If AI-PM intentionally requests a new generation after a terminal Job, it MUST create a new caller_request_id and a new Idempotency-Key.
- The request fingerprint MUST cover the authenticated tenant/project scope, artifact_id, generator_id, and canonical semantic request body (including input, options, and expected_current_version_id). Transport-only fields and trace IDs are excluded.

The Artifact Service MUST derive tenant/project scope from its validated request/delegation context, not trust caller-supplied scope fields.

### 2.3 Durable uniqueness and conflict behavior

Persist the caller identity on the GenerationJob row or in a durable correlation table with a non-expiring foreign key to the Job.

Recommended uniqueness:

`UNIQUE (tenant_id, project_id, caller_request_id)`

The UUID is generated by the AI-PM service and scoped to its authorized project. If the product later supports multiple independent API clients per project that must not share a correlation namespace, add a server-derived authenticated caller namespace; do not accept an arbitrary caller namespace as an authorization claim.

For a repeated create request:

- Same scope + same caller_request_id + same canonical request fingerprint: return the original GenerationJob (200 replay or 202 existing-job response; exact status code should follow the existing API convention).
- Same scope + same caller_request_id + different fingerprint: return 409 `CALLER_REQUEST_ID_REUSED`.
- Same caller_request_id under a different tenant/project: it is a separate scope and MUST NOT disclose the other Job.
- Concurrent requests with the same identity must serialize on the unique constraint and converge on exactly one Job.

The durable record MUST NOT expire with the 24-hour idempotency cache. Its retention must be at least as long as the referenced Job can be queried or audited. If Job archival/deletion is introduced later, the correlation tombstone must remain for the documented reconciliation/audit horizon and must never silently become reusable.

### 2.4 Lookup endpoint

Add:

`GET /v1/generation-jobs/by-caller-request/{caller_request_id}`

Required behavior:

- Require the same bearer delegation and `X-Project-Id` scope checks as `GET /v1/generation-jobs/{job_id}`.
- Resolve only within the authenticated tenant/project scope.
- Return the normal GenerationJob response when found.
- Return 404 when no record exists in that authorized scope.
- Do not reveal whether the same UUID exists in another tenant/project.
- The lookup is read-only and returns the current authoritative Job state; it does not create or retry a Job.

The path is deliberately caller-oriented. AI-PM does not need to know or reconstruct Artifact Service database keys.

### 2.5 Recovery algorithm for AI-PM

AI-PM MUST persist a local operation record before the first API call, including caller_request_id, idempotency key, immutable request hash/reference, artifact_id, and operation state.

On uncertain create outcome (timeout, connection reset, process restart, or lost response):

1. Query the lookup endpoint using caller_request_id.
2. If found, persist the returned job_id and continue polling that Job.
3. If 404, retry POST with the same caller_request_id, same Idempotency-Key, and identical semantic body.
4. If the POST races with another retry, the durable unique constraint makes both requests converge on the same Job.
5. If 409 fingerprint conflict, stop automatic retries and raise an integrity/reconciliation error. Never mint a new ID merely to get past the conflict.
6. If lookup is unavailable, retain the operation as unresolved and retry lookup with bounded backoff. Do not create a replacement Job.

A 404 followed by a retry is safe only because the create path and lookup share the same durable uniqueness transaction. The server must not return 404 while a committed Job with that caller_request_id exists.

The short-lived Idempotency-Key remains useful for exact response replay, but recovery correctness no longer depends on its retention window.

## 3. AR04-02 — Exact Job-to-Version provenance

### 3.1 Public field

Add this additive field to the GenerationJob response and Rust DTO:

`target_version_id: Option<Uuid>`

It exposes the existing internal `GenerationJob.target_version_id`; it is not a new client-generated identifier and is not derived from Artifact.current_version_id.

Semantics:

- `null`: the Job has not yet allocated/selected its target Version, or no target Version exists for this Job.
- non-null: the immutable Version identity reserved/created for this Job.
- Once non-null, the value MUST NOT change for the lifetime of the Job.
- A Version ID MUST never be shared by two GenerationJobs.
- On `succeeded`, target_version_id MUST be non-null and identify exactly one Version belonging to the Job's artifact and tenant/project scope.
- On `succeeded`, that Version MUST be READY and its Output manifest must be committed and queryable.
- A failed/cancelled/timed_out Job may have null or non-null target_version_id depending on how far it progressed; the referenced Version must never be represented as READY unless the normal upload/finalize/commit checks succeeded.

The field may be null in the initial 202 response and become populated in later GET responses if the implementation allocates the Version during execution. Consumers must therefore treat the Job response as a current snapshot and persist the non-null target_version_id once observed.

### 3.2 Result consumption

When Job status is `succeeded`, AI-PM MUST:

1. Require non-null target_version_id; missing value is a protocol-integrity failure, not a reason to fall back to current_version_id.
2. Fetch that exact Version by `GET /v1/artifacts/{artifact_id}/versions/{version_id}`.
3. Verify the returned Version belongs to the expected artifact and is READY.
4. Read its Output manifest and perform AI-PM business validation/approval separately.
5. Persist the exact artifact_id + generation_job_id + target_version_id association in its own business mapping.

AI-PM MUST NOT infer the result Version from the mutable Artifact.current_version_id. The current pointer is a user-facing selection, not Job provenance.

### 3.3 Required server-side invariant

The Artifact Service completion transaction MUST enforce all of the following atomically:

- The completing Attempt is still current and its lease/fencing token is valid.
- Cancellation has not won the state arbitration.
- The Job has one target Version associated with the same artifact and scope.
- The Version is committed READY only after File Service upload/finalize and output verification succeed.
- The Job transitions to succeeded only after the exact Version and Output manifest are committed.
- The Job's target_version_id and succeeded state become visible consistently.

If any required condition fails, the Job MUST NOT report succeeded. The existing LMMS delegation and File Service finalize P0 gates remain in force; this contract does not bypass them.

## 4. API / persistence / test impact (future implementation)

This is a contract proposal, not a claim that the following changes exist.

Artifact Service implementation will need to:

- Extend CreateGenerationJobRequest and OpenAPI with required caller_request_id.
- Add durable uniqueness and lookup support, either a GenerationJob column + unique index or a dedicated non-expiring correlation table.
- Make create and lookup race-safe under concurrent requests.
- Add `CALLER_REQUEST_ID_REUSED` to the stable error contract and tests.
- Expose target_version_id in OpenAPI GenerationJob schema, Rust DTO, response mapping, SDK, and tests.
- Add a database/application invariant preventing succeeded Jobs without a valid target Version and committed Output.
- Keep idempotency_record expiry semantics separate; do not silently change the documented 24-hour HTTP replay contract.

AI-PM implementation will need to:

- Persist caller_request_id before outbound create.
- Use lookup-first reconciliation after uncertain outcomes.
- Persist target_version_id only from the authoritative Job response.
- Treat succeeded + null target_version_id as a protocol violation.
- Keep its own business-record ↔ generic artifact_id ↔ exact version_id mapping.

## 5. Contract test matrix

| Scenario | Expected result |
|---|---|
| First create with caller_request_id A | One Job created |
| Concurrent duplicate create A, same body | Both callers resolve to the same Job ID |
| Repeated create A, same body after Idempotency-Key expiry | Same Job returned; no duplicate |
| Repeated create A, different body | 409 CALLER_REQUEST_ID_REUSED |
| Lookup A in same tenant/project | Original Job returned |
| Lookup A in another tenant/project | 404; no existence disclosure |
| Lost create response, lookup finds Job | AI-PM resumes existing Job |
| Lost create response, lookup 404, retry races original | Unique constraint converges to one Job |
| Job queued/running before target Version allocation | target_version_id may be null |
| Job succeeds | target_version_id is non-null, immutable, same-scope, READY Version |
| Current pointer changes after Job success | target_version_id remains unchanged |
| Job cancelled/failed before Version commit | Job is not succeeded; no false READY result |
| Attempt lease is stale or cancellation wins | Completion cannot publish Version/Job success |

## 6. Explicit non-goals and remaining gates

ART-04A does not:

- change who owns business intent or Job state;
- add a distributed transaction, shared database, RabbitMQ, or webhook;
- make AI-PM write Artifact Service Job/Version tables;
- resolve AI-PM Visualization mapping schema/cutover (AR04-03);
- implement SDK methods or AI-PM consumer orchestration (AR04-04/05);
- authorize SeeCode Adapter implementation or production generation enablement;
- close LMMS delegation, File Service upload/finalize, or ART-03B-02/03 runtime lifecycle blockers.
