## 2. SQL 与数据库状态机复核

### 2.1 DB-BLOCKER-01 的推荐方案与现有状态约束相容

复核事实：
- 0001 的 `guard_job_transition` 允许 `running → cancelled`、`running → retry_wait`、`retry_wait → cancelled`、`retry_wait → queued`。
- 0003 的 heartbeat 确实先检查 deadline，再检查 cancel。
- 0003 的 `settle_failed_attempt` 可把 Attempt 结算并把 Job 推入 retry_wait；该函数不清除 cancel_requested_at。
- 0003 的 claim 明确要求 `cancel_requested_at IS NULL`。
- 0003 的 request cancel 对 queued/retry_wait 直接转 cancelled；对 running 只登记 cancel_requested_at。
- 0003 recovery 在 lease expired 且 Job running + cancel_requested_at 非空时，会把 Job 置 cancelled。

结论：
- 推荐的“取消先提交 → heartbeat 先观察 cancel → 不做 timeout retry settlement”可以消除已发现的不可领取状态。
- “deadline settlement 先提交 → 后续 cancel request 将 retry_wait 转 cancelled”也被 0001 的状态转换守卫允许。
- 需要在新 Migration 中增加数据库级不变量保护，避免未来其他写路径再次产生 `queued/retry_wait + cancel_requested_at`；建议先审计历史行，再约束/修复，不能静默清理。
- 必须对 heartbeat、cancel request、recovery 的真实并发执行进行 PostgreSQL 测试。

**状态：设计方向成立；数据库缺陷尚未关闭。**

### 2.2 DB-BLOCKER-02 的时间映射推导

复核推导：
- DB 在函数末尾用 `clock_timestamp()` 计算 D−t_db 的剩余 duration；
- Worker 在 RPC 发出前记录 t_send；
- t_db 不早于 t_send；
- Worker 使用 t_send + returned_remaining − guard 作为本机 cutoff；
- 因为 RPC 请求、DB 执行、事务提交、响应传输都包含在 Worker 从 t_send 到收到响应的经过时间中，不能把响应接收时刻作为新的 duration 起点。

该方案在同一单调时钟频率域下是保守的；它不依赖 DB 与 Worker wall clock 对齐。

本轮额外补充了两个必要约束：
- 使用暂停感知 monotonic clock，不能默认 Stopwatch/CLOCK_MONOTONIC 一定计入系统睡眠；
- DB 与 Worker monotonic clock 的最大相对频率误差必须进入 safety margin，不能假设两者完全同频。

剩余风险：
- 必须在目标 OS/VM/容器运行环境验证时钟源、精度、睡眠/暂停语义和频率误差上界；
- DB 自身 wall clock 大幅回拨/跳跃仍是基础设施风险；
- claim/heartbeat 版本化响应结构、NULL/0/舍入规则和 SDK 兼容策略尚未实现。

**状态：时间契约方向成立；数据库与平台契约尚未关闭。**

## 3. Supervisor FSM 复核

本轮确认 v2.2 已显式覆盖：
- claim RPC 已提交但响应丢失；
- spawn API 结果不确定/进程句柄丢失；
- heartbeat 的 renewed/cancel_requested/deadline_exceeded/stale；
- 明确 DB 错误与传输不确定的分类；
- complete/fail 不确定后的单次 probe 与单次补交；
- probe 后 lease 在补交前过期；
- 原终态 RPC 在客户端超时后仍可能于 DB 端执行，与补交竞争；
- confirm not_requested；
- 死亡确认失败；
- 活进程目录 TTL 清理；
- Worker crash、VM suspend/resume；
- Linux setsid/双重 fork 逃逸、Windows breakaway/句柄继承/嵌套 Job。

补充的关键并发说明：
- 客户端 RPC timeout 不等于 DB 后端事务取消；
- probe renewed 是点时观察，原请求可能仍在 DB 端排队；
- 只允许原参数完全相同的一次补交；
- 原请求与补交必须通过 Attempt/Job 行锁串行化，最终只有一个能完成状态转换；
- 该结论必须用真实 PostgreSQL 并发测试证明。

**状态：设计路径显著完整；实现级调用次数/锁竞争证明尚未完成。**

## 4. Lease/Heartbeat 时序复核

- v2.1 对原参数组的否决仍然成立：L=60、H=15、T=10、K=2、M=12 时，2×(15+10)=50，大于 L−M=48。
- v2.2 采用保守公式 `K × (H + T) + J + S_kill + G < L`，并将调度抖动、kill/死亡确认预算和额外余量显式列出。
- v2.2 没有擅自给出“看起来可用”的最终参数值，这是正确的；必须等待真实运行时测量。
- heartbeat 不重叠、timeout 计数何时清零、响应晚于 cutoff 的处理，都已成为明确不变量/测试项。

**状态：公式方向正确；TIMING-BLOCKER-03 仍未关闭，因为参数与实测上界尚不存在。**
