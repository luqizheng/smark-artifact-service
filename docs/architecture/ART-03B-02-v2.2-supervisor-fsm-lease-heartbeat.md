# ART-03B-02 — v2.2 Supervisor FSM 与 Lease/Heartbeat 统一设计

## 1. 目标与非目标

目标：
- 一个 Supervisor 负责一个 Attempt 的本地生命周期；
- DB 是 Job/Attempt 状态、lease、deadline、取消请求和终态的唯一权威；
- Worker 通过受控函数协调，不直接 DML；
- Executor 只执行受限计算；Supervisor 控制进程创建、终止、结果冻结与 DB 提交；
- 所有 RPC 不确定性、deadline、lease、取消、进程死亡确认与清理路径均显式建模；
- 任何无法证明执行权仍有效的路径都 fail closed。

非目标：
- 不把 Supervisor 本地状态变成 Job 状态权威；
- 不在 Worker 直接修改业务表；
- 不允许 Executor 访问 Artifact API、LMMS File Service、AI-PM 或外部业务副作用；
- 不解决 03B-03 的 cgroup/容器隔离实现，不替代 03D 的文件上传/finalize/READY 协议；
- 不把 DB-BLOCKER-01/02 的候选设计当作已部署事实。

## 2. 规范对象与不变量

### 2.1 Attempt ownership

DB claim 成功后产生：
- job_id、attempt_id、attempt_number；
- 一次性 lease token（仅明文交给当前 Worker；DB 只保存 hash）；
- lease 与 deadline 的 DB 权威截止点；
- 输入/选项快照与 generator 版本信息。

Worker 的本地 Attempt context 只能保存执行所需信息与单调时钟 cutoff；不能自行推断 DB Job 状态。

### 2.2 核心不变量

| ID | 不变量 |
|---|---|
| INV-FSM-01 | 每个 Supervisor 同时最多管理一个 Attempt；同一 Job 同时最多一个有效 Attempt，由 DB 原子 claim 保证 |
| INV-FSM-02 | 没有 claim 响应/有效 token，绝不 spawn Executor |
| INV-FSM-03 | claim RPC 传输不确定时，不假定没有 claim；本轮不再次 claim 以“补拿”同一个 Job |
| INV-FSM-04 | 只有 DB heartbeat renewed 才能更新本地 lease/deadline cutoff |
| INV-FSM-05 | 所有 cutoff 只使用 monotonic clock；禁止使用本机 wall clock 比较 DB 时间戳 |
| INV-FSM-06 | cancel_requested、deadline_exceeded、stale、cutoff 到期、协议错误均进入 KillOnly；KillOnly 后不再运行 Executor |
| INV-FSM-07 | deadline_exceeded 表示 DB 已执行 settlement；Worker 零 DB 写 |
| INV-FSM-08 | stale 不表示业务成功或失败；Worker 停止写并等待 DB/recovery 权威收敛 |
| INV-FSM-09 | complete/fail 只能在 Executor 已退出、死亡确认成功、输出快照冻结之后提交 |
| INV-FSM-10 | 传输不确定的终态提交最多一次 probe、最多一次原参数补交；不允许第三次提交 |
| INV-FSM-11 | confirm_generation_job_cancelled 只在死亡确认成功且 cancel_requested 分支调用，最多一次；not_requested 不重试 |
| INV-FSM-12 | 不能确认进程树死亡时，不 confirm、不清理 Attempt 目录、不提交成功/失败 |
| INV-FSM-13 | Executor 不拥有 DB token、File Service token、云凭据或服务 socket；不能绕过 Supervisor 产生业务副作用 |
| INV-FSM-14 | Supervisor crash 后不恢复旧 Attempt 执行资格；由平台进程回收 + DB recovery 收敛 |
| INV-FSM-15 | queued/retry_wait 与非空 cancel_requested_at 不得共存（待 DB-BLOCKER-01 新契约落实） |

## 3. 状态模型

本状态机分为三个正交维度，避免把 DB 业务状态与本地进程状态混成一个枚举：

1. **Coordinator state**：claim/RPC/DB 协议阶段；
2. **Process state**：Executor 是否创建、运行、终止、确认死亡；
3. **Artifact submission state**：输出是否冻结、终态请求是否提交/不确定。

本地状态仅用于 Supervisor 控制流程，不是持久业务权威。

### 3.1 Coordinator state

`Idle → Claiming → Claimed → Executing → Stopping → Settling → Settled`

异常/旁路：
- `ClaimUncertain`
- `Abandon`
- `AbandonPendingRecovery`
- `Degraded`

### 3.2 Process state

`NotCreated → Starting → Running → KillOnly → Exited → DeathConfirmed`

异常：
- `SpawnUncertain`：spawn API 返回不确定或句柄丢失；
- `DeathUnconfirmed`：终止已发出但无法证明进程树已退出。

### 3.3 Submission state

`NoOutput → OutputFrozen → SubmitInFlight → SubmitUncertain → ProbeInFlight → RetryOnceInFlight → SubmissionResolved`

不允许从 RetryOnceInFlight 再次进入 SubmitUncertain 后继续重试；只能 Abandon。

## 5. RPC 结果分类与调用次数上界

### 5.1 结果分类

每次 RPC 必须归类为以下一种：
- **Success response**：收到且 schema/关联 ID 正确的受控函数结果；
- **Transport uncertain**：可能已到达 DB，可能提交，但响应未可靠收到；
- **Explicit DB rejection**：收到确定的 PostgreSQL SQLSTATE/业务错误；
- **Local protocol failure**：序列化、字段验证、版本不兼容、响应关联错误；
- **Local cancellation/shutdown**：本地停止流程导致调用取消，必须判断请求是否已发送；发送后即按 transport uncertain 处理。

不能把所有异常都归为 Uncertain。

### 5.2 传输超时后原请求仍可能在 DB 端执行

客户端超时/取消等待，不等于 PostgreSQL 后端事务已取消。原 complete/fail 请求可能仍在网络、连接池或 DB 锁队列中。

因此 probe=renewed 是**探针事务取得 Attempt/Job 锁时的点时观察**，不证明先前请求在所有服务器端执行路径上都已消失。原请求与唯一一次补交可能并发竞争，但必须满足：
- 两者使用完全相同的 RPC 类型、job_id、attempt_id、lease token、错误码/输出 SHA 与冻结快照；
- DB 函数都先锁同一 Attempt，再锁同一 Job，并在锁内校验 status/token/lease；
- 只有一个请求能把 running Attempt/Job 转成终态或 retry_wait；另一个必须得到 stale/stale_attempt；
- 该结论必须由真实 PostgreSQL 并发测试证明，不能仅凭应用层互斥声称；
- 补交返回 stale 或再次不确定后，Supervisor 不再提交，等待权威状态收敛。

这允许“原请求晚到”与“补交先到”两种顺序，但不允许两次终态转换，也不允许不同参数的第二次请求。

### 5.2 终态 RPC 上界

| RPC | 正常次数 | 不确定处理 | 最大次数 |
|---|---:|---|---:|
| claim | 每轮 1 | 不重试当前 claim；等待 recovery | 1 |
| heartbeat | 按 H 调度 | 受 K 次连续 timeout 上界限制；任何 cutoff 到期立即 KillOnly | 运行期间有界 |
| complete | 1 | 仅传输不确定时 probe 1 次；renewed 后补交 1 次 | 2 |
| fail | 1 | 同 complete | 2 |
| confirm cancel | 1 | 不因 not_requested/stale 重试；传输不确定不盲目重复，等待 recovery | 1 |
| probe heartbeat | 仅终态提交传输不确定时 1 | probe 本身不确定则 abandon | 1 |

complete 与 fail 对同一 Attempt 互斥；不能各调用一次。任何 Attempt 不得先 fail 再 complete，或先 complete 再 fail。

## 6. Lease / Deadline 本机映射

### 6.1 数据库返回

采用 DB-BLOCKER-02 候选契约：
- claim 返回 lease_remaining_ms、deadline_remaining_ms；
- heartbeat renewed 返回同一时点的两个剩余时长；
- 使用 DB clock_timestamp() 在函数关键更新之后计算；
- duration 向下取整；0 表示已到期；
- cancel_requested 不续租；deadline_exceeded 已完成 DB settlement；stale 不再拥有执行权。

### 6.2 本机计算

每次 claim/heartbeat RPC 发出前记录 monotonic `t_send`。对每个 DB remaining duration：

`local_cutoff = t_send + remaining_duration - guard`

收到响应时若已经超过 cutoff，立即 KillOnly。不得使用 `t_receive + remaining`。effective cutoff 为 lease cutoff 与 deadline cutoff 的较早者。

### 6.3 Heartbeat 调度

参数必须满足固定 Delay 调度最坏预算，且给调度抖动和进程终止留出空间：

`K × (H + T) + J + S_kill + G < L`

其中：
- L：heartbeat 成功后 DB 返回的完整 lease duration（若 deadline clamp，则以更早的 deadline cutoff 为准）；
- H：每次 RPC timeout/完成后等待的固定 Delay；
- T：单次 RPC timeout；
- K：连续 RPC timeout 阈值；
- J：调度抖动/线程饥饿预算；
- S_kill：从发出 kill 到死亡确认成功的实测上界；
- G：额外安全余量。

当前 v2 参数 L=60,H=15,T=10,K=2,M=12 不成立：2×(15+10)=50，大于 60−12=48。旧参数禁止沿用。

Supervisor 必须证明：
- heartbeat RPC 不重叠；
- timeout 计数只在明确 renewed 后清零；
- heartbeat 返回 cancel/deadline/stale 不清零后继续；
- 线程调度延迟纳入 J；
- 达到 cutoff 时本地 kill timer 可优先执行；若无法保证优先级，支持环境不满足安全条件。

## 7. 输出冻结与副作用边界

- Executor 退出并完成死亡确认后，Supervisor 才冻结输出目录与摘要。
- 输出快照包括文件列表、大小、SHA-256、stdout/stderr 摘要和生成元数据；冻结后只读，不允许 Executor 或其他 Attempt 改写。
- complete/fail 的补交必须复用完全相同的请求字节/参数和快照。
- Executor 无网络/无凭据仍不足以证明没有副作用；03B-03 必须实测 network namespace/firewall deny、只读根、mount allowlist、cgroup/container、资源限制与宿主控制面隔离。
- Artifact 上传/finalize/安全检查/READY 只允许 03D 服务路径执行；Supervisor/Executor 不直接发布 Artifact。

## 8. 进程树终止与死亡确认

### Linux
- 进程组只作为第一层便利机制，不作为安全证明；
- PDEATHSIG 不保证未配合的孙进程；
- PID 1 只回收孤儿僵尸，不杀活进程；
- 生产硬边界是 03B-03 cgroup v2 / 容器销毁；Executor 无权迁移自身或访问宿主 cgroup 控制面；
- 无 cgroup 的开发环境若检测到脱组/逃逸或无法完整枚举后代，死亡确认失败，fail closed。

### Windows
- CREATE_SUSPENDED → AssignProcessToJobObject → Resume；
- 禁止 BREAKAWAY/SILENT_BREAKAWAY；
- Job 句柄不可继承/复制；最后一个句柄关闭触发 KILL_ON_JOB_CLOSE；
- 明确嵌套 Job 不兼容时 fail-fast；
- 测试多代子进程、双重 spawn、Supervisor crash 与最后句柄关闭。

死亡确认失败：停止 heartbeat，不调用 confirm/complete/fail，不清理 Attempt 目录，等待 DB lease/recovery；不能承诺取消终态的固定完成时限。

## 9. Attempt 目录生命周期

- 目录按 Attempt 唯一隔离，Executor 只能写自己的工作子目录；
- Supervisor 保留控制目录、IPC 与凭据边界，Executor 不可访问；
- 进程死亡确认成功后，目录可以进入延迟清理队列；
- 进程死亡未确认时，禁止按 mtime/TTL 删除目录；
- 若采用容器/临时 volume，必须证明销毁语义覆盖所有后代进程及挂载，且不会删除共享数据；
- Supervisor crash 后由平台回收与独立清理器协同；清理器不能仅凭 DB terminal status 假设本地进程已死。

## 13. DB cancelled 与平台进程清理的双重生命周期（与 DB-BLOCKER-01 设计复审对齐）

本节补充取消终态语义，与 PR #5 的 DB-BLOCKER-01 Migration 0004 设计复审保持一致；若本文其他段落可能被理解为 Job cancelled 等于 OS 进程死亡，以本节为准。

### 13.1 两种不同的终态事实

- **DB cancellation settled**：数据库已撤销 Job 的重新调度资格和当前 Attempt 的结果提交资格。Job/Attempt 的 cancelled 只表达这一事实。
- **Process tree death confirmed**：平台硬隔离单元（Linux cgroup v2/container；Windows Job Object）已由可信控制面确认不存在存活 Executor 及其后代。

DB cancelled 不构成 Process tree death confirmed 的证据。Recovery 可以在 Lease 到期后先把 DB 状态收敛为 cancelled；此时只代表旧 Attempt 不能再提交或恢复执行权。进程可能仍在平台回收窗口内，但必须被限制为无网络、无凭据、无业务副作用的纯计算单元。

### 13.2 允许 DB 先收敛的强制前提

生产实现必须由独立于 Worker/Supervisor 进程的 runtime/controller 持有或恢复每个 Attempt 隔离单元的销毁能力。Worker/Supervisor 崩溃、重启或 DB recovery 完成，不得导致 cgroup/container 失去可定位性或无人负责。

必须具备：
- 每 Attempt 独立且不可逃逸的硬隔离单元；
- Executor 无网络、无业务凭据、无 Artifact/LMMS/AI-PM 访问能力，且不能自行发布输出；
- 只有 Supervisor 在 Process tree death confirmed 后才能冻结/提交输出；
- KillOnly 后关闭 IPC/结果通道；
- 外部 controller 在 Worker/Supervisor 崩溃后仍能回收隔离单元，具备有界回收 SLA、失败告警和人工隔离；
- controller 确认死亡后才允许清理 Attempt 目录。

若平台不能证明这些前提，生产执行必须 fail closed；不得退化为只杀进程组，也不得把 DB cancelled 当作目录清理许可。

### 13.3 与本 FSM 的状态映射

- KillOnly → Stopping → DeathConfirmed：Supervisor 已获得 OS 级死亡证据，允许按正常路径冻结输出或调用一次 confirm。
- DeathUnconfirmed：停止 heartbeat；不 confirm、不 complete、不 fail、不提交输出；不清理 Attempt 目录；把隔离单元交给外部 controller。
- DB recovery 将 Job/Attempt 置 cancelled 后，Supervisor 本地仍可处于 DeathUnconfirmed；两者并不矛盾。
- Attempt 目录清理由独立 ProcessCleanup 证据驱动，不得只根据 Job.status 或 Attempt.status=cancelled 触发。

### 13.4 Lease 过期后的取消收敛

heartbeat 在持有 Attempt 锁、验证 Attempt=running/token、持有 Job 锁并验证 Job=running 后，若 cancel_requested_at 非空，可返回 cancel_requested，即使 lease_expires_at 已过期；此分支不续租、不写 heartbeat、不执行 settlement，只允许 KillOnly/confirm。若 recovery 先把 Attempt 改为 lease_expired，后续 heartbeat/confirm 必须 stale。

该行为不恢复租约或执行权。Supervisor 必须禁止 spawn/resume/Executor 操作，只能终止隔离单元；死亡未确认则交给外部 controller。此顺序及 confirm/recovery 竞争必须通过真实 PostgreSQL 多连接测试。

### 13.5 新增平台验收

除原 FSM-T01–T24 外，必须覆盖：
- Lease 过期 + cancel 已提交 + Recovery 尚未锁 Attempt：heartbeat 返回 cancel_requested 且不续租；
- Recovery 先把 Attempt 改为 lease_expired：heartbeat/confirm 返回 stale；
- confirm 与 recovery 两种锁先后顺序，各自只有一个合法终态；
- DB cancelled 但进程仍存活：无提交能力、无 IPC 命令、无目录清理；
- Worker/Supervisor 崩溃后 controller 仍可定位并销毁隔离单元；
- controller 重启、重复回收、隔离单元不存在、控制面超时均幂等且可审计；
- 只有 death-confirmed 的 Attempt 才允许冻结输出或清理目录。

**本节是设计契约，不是平台实现证据。PROCESS-BLOCKER-04 仍未关闭，PR #4 继续 Draft，不得据此启动 Worker 实施。**
